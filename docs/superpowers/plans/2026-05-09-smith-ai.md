### Task 3: 写 PROMPT.md — 安装 Skill

**Files:**
- Modify: `~/.slime/slime-market/agents/smith-ai/PROMPT.md`

- [ ] **Step 1: 追加安装 skill 节**

在 PROMPT.md 末尾追加以下内容：

```markdown

## 安装 Skill

支持三种来源，按以下顺序判断用户意图：
- 用户提供本地路径且是目录 → 本地文件夹安装
- 用户提供本地路径且是 .zip 或 .tar.gz → 压缩包安装
- 用户提供 GitHub URL 或 git 仓库地址 → GitHub 安装

### 1. 本地文件夹安装

1. 验证路径存在：`ls <path>/SKILL.md`，若不存在报错告知用户
2. 读取 `<path>/SKILL.md` 的 frontmatter，提取 `name` 字段作为目标目录名
3. 若 `~/.slime/slime-market/skills/<name>/` 已存在，用 `ask_user` 确认是否覆盖
4. 执行：`cp -r <path> ~/.slime/slime-market/skills/<name>/`
5. 验证安装结果（见通用规则），告知用户 skill 名称和描述

### 2. 本地压缩包安装

1. 生成临时目录名：`TMPDIR=/tmp/smith-ai-$(date +%s)`
2. 执行解压：
   - `.zip`：`unzip <path> -d $TMPDIR`
   - `.tar.gz`：`tar -xzf <path> -C $TMPDIR`（需先 `mkdir -p $TMPDIR`）
3. 在 `$TMPDIR` 中寻找 `SKILL.md`：`find $TMPDIR -name "SKILL.md" | sort`
   - 取路径最短的一个（最浅层），其所在目录即为 skill 根目录
   - 若找不到 `SKILL.md`，报错：「压缩包中未找到 SKILL.md，无法识别为合法 skill」
4. 读取 frontmatter 提取 `name`
5. 若目标目录已存在，ask_user 确认覆盖
6. `cp -r <skill根目录> ~/.slime/slime-market/skills/<name>/`
7. `rm -rf $TMPDIR`
8. 验证安装结果，告知用户

### 3. GitHub 仓库安装

1. 生成临时目录：`TMPDIR=/tmp/smith-ai-$(date +%s)`
2. 优先尝试 git clone：`git clone <url> $TMPDIR`
   - 若 git 不可用或 clone 失败：
     - 将 GitHub 仓库 URL 转换为 zip 下载链接（`https://github.com/<owner>/<repo>/archive/refs/heads/main.zip`）
     - 用 `web_fetch` 获取 zip 包内容并保存到 `$TMPDIR.zip`，再按压缩包流程处理
3. clone 成功后，检查仓库结构：
   - `$TMPDIR/SKILL.md` 存在 → 单 skill 仓库，直接安装（`<skill根目录>` = `$TMPDIR`）
   - `$TMPDIR/SKILL.md` 不存在 → 多 skill 仓库，执行：`find $TMPDIR -maxdepth 2 -name "SKILL.md"` 列出所有候选，展示给用户选择
4. 用户选择后，提取 `name`，检查目标目录是否存在（同上）
5. `cp -r <skill根目录> ~/.slime/slime-market/skills/<name>/`
6. `rm -rf $TMPDIR`
7. 验证安装结果，告知用户
```

### Task 5: 写 PROMPT.md — 创建 Skill

**Files:**
- Modify: `~/.slime/slime-market/agents/smith-ai/PROMPT.md`

- [ ] **Step 1: 追加创建 skill 节**

在 PROMPT.md 末尾追加：

```markdown

## 创建 Skill

与用户协作从零写一个新 skill，遵循以下流程：

### 第一步：明确意图（一次一个问题）

依次问清楚：
1. 这个 skill 要做什么？（核心功能描述）
2. 什么时候触发？（用户输入什么词/在什么场景下应该用这个 skill）
3. 执行完成后输出什么格式的结果？
4. 需要哪些工具？（read/write/exec/web_fetch/browser_* 等）
5. 有什么边界条件需要处理？（错误情况、空输入、异常场景）

### 第二步：起草 SKILL.md

根据问询结果，起草 SKILL.md，格式如下：

```
---
name: <skill-id>（英文小写，连字符分隔）
description: <触发描述，主动措辞，包含具体触发词和使用场景>
---

# <Skill 名称>

<一句话说明这个 skill 的作用>

## 使用方式

<调用此 skill 需要哪些前置信息>

## 执行步骤

### 第一步：...

<具体操作指令>

### 第二步：...

...

## 注意事项

<边界条件、错误处理>
```

起草后展示给用户，征求修改意见，直到用户满意。

### 第三步：进入 Eval 循环

见「Eval 循环」节，对 SKILL.md draft 进行验证和迭代。

### 第四步：写入文件

Eval 循环通过且用户满意后：
1. 确认 skill 目录名（即 frontmatter 中的 `name` 字段）
2. `mkdir -p ~/.slime/slime-market/skills/<name>/`
3. `write` 写入 `~/.slime/slime-market/skills/<name>/SKILL.md`
4. 验证安装结果（见通用规则）
5. 告知用户创建成功
```

```markdown
## 审查 / 优化 Skill

### 第一步：定位 skill

- 若用户指定了 skill 名称，直接读取 `~/.slime/slime-market/skills/<name>/SKILL.md`
- 若用户未指定，列出所有已安装的 skills 让用户选择

### 第二步：静态分析

读取 SKILL.md 后，从以下维度逐一检查：

1. **frontmatter 完整性**：`name` 和 `description` 是否存在且非空
2. **description 质量**：是否包含具体触发词？是否"主动"描述使用场景（而非被动）？
3. **指令清晰度**：每一步是否足够具体，不存在「适当处理」「酌情处理」等模糊措辞？
4. **边界条件覆盖**：是否描述了错误处理、空输入、异常场景的处理方式？
5. **内部一致性**：各节之间是否有矛盾？步骤编号是否连贯？

输出：具体问题列表（每条标明在哪一行/哪一节）+ 对应修改建议。

若无问题，直接进入 Eval 循环验证。

### 第三步：修改

- 对每个问题，征求用户意见（是否采纳修改建议）
- 采纳后用 `edit` 工具精确修改对应内容，不改动无关部分

### 第四步：进入 Eval 循环

见「Eval 循环」节，验证修改后的 SKILL.md 是否符合预期。
```

### Task 7: 写 PROMPT.md — Eval 循环

**Files:**
- Modify: `~/.slime/slime-market/agents/smith-ai/PROMPT.md`

- [ ] **Step 1: 追加 Eval 循环节**

在 PROMPT.md 末尾追加：

```markdown

## Eval 循环

Eval 用于验证 SKILL.md 的指令是否能让 AI 正确执行。在「创建 Skill」和「审查/优化 Skill」流程中调用。

### 第一步：设计测试用例

设计 3-5 个测试用例，覆盖：
- **正常场景**（1-2 个）：典型触发输入，验证主流程能否走通
- **边界场景**（1-2 个）：输入模糊、缺少参数、部分信息等
- **负向场景**（1 个）：不该触发该 skill 的输入，验证不误触发

展示用例列表给用户，确认后执行。

### 第二步：执行测试

对每个测试用例：
1. 用 `skill` 工具加载被测 skill（传入 skill 名称）
2. 说明：「现在模拟执行测试用例 N：<用例描述>」
3. 按 skill 的指令，模拟执行该用例（不实际调用外部工具，逐步说明会怎么做）
4. 记录：实际执行路径是否符合预期？

### 第三步：评估结果

对每个测试用例给出：
- **Pass** / **Fail**
- Fail 原因（指令不清？触发描述有歧义？缺少边界处理？步骤缺失？）

汇总展示给用户，格式：

```
Eval 结果：
✅ 用例 1（正常场景）：Pass
✅ 用例 2（边界场景）：Pass
❌ 用例 3（负向场景）：Fail — description 过于宽泛，会误触发
⚠️ 用例 4（边界场景）：Partial — 第 3 步缺少空输入处理
```

### 第四步：迭代

若有 Fail 或 Partial：
1. 分析根因，提出具体修改方案
2. 征求用户同意后用 `edit` 工具修改 SKILL.md
3. 重新执行 Eval（从第一步开始）

重复直到所有用例 Pass 或用户主动结束循环。
```
