chat() 执行时序 — 正常路径 vs 错误路径

正常工作的部分

  • ✓ per-session AbortController 独立
  • ✓ RESPONSE 事件有 sessionId 过滤
  • ✓ ERROR 事件有 sessionId 过滤
  • ✓ agentic loop tool call 内存维护正确
  • ✓ 乐观插入 user 消息即时渲染
  • ✓ retryLast 本地即时移除 assistant

已知 Bug 根因

  • A user 先写 DB 再 buildContext → 重复
  • B abort 时 assistant 消息不落 DB
  • C END 不过滤 sessionId → isGenerating 误置
  • D chat() 无并发入口保护
  • E 历史 tool_call 退化为纯文本传给 LLM

修复方向

  • A 先 buildContext，再写 user 到 DB
  • B abort 分支也 createMessage(assistant)
  • C END handler 加 sessionId === activeId 判断
  • D chat() 开头检查 sessionState === generating
  • E 历史重建用结构化 tool-call parts（可选）
BUG A · 消息重复

user 消息被发送两次

chat() 第 216 行先调 createMessage(db, {role:"user",...}) 将消息写入 DB， 紧接着第 226 行调 buildContext(sessionId, content, db)。 buildContext 内部 listBySession(db, sessionId) 读出全部历史， 此时刚写入的 user 消息已经在其中，最终构建的 messages 末尾变为： ...history, {role:"user", content}, {role:"user", content}—— 同一条消息出现两次，LLM 报 "No output generated" 或返回空。

修复：交换顺序——先 buildContext（此时 DB 无当前 user 消息），再 createMessage。
BUG B · assistant 消息丢失

abort 后刷新只剩 user 消息

stopGeneration() 触发 AbortController，chat() catch 分支检测到 abortSignal.aborted 后直接推 END 事件然后 return， 不写 assistant 消息到 DB。 END 事件触发 fetchMessages 重新从 DB 加载，此时只有 user 消息， 已经渲染的 streaming blocks 被清空，用户看到对话"缺一半"。

修复：abort 分支中，若 blocks 非空，同样 createMessage(assistant, blocks, status:"aborted")。
BUG C · 状态错误重置

isGenerating 被其他 session END 误清

agentChatIpc.ts 第 44 行：store.isGenerating = false 在 END handler 中无条件执行，不检查 d.sessionId === activeSessionId()。 若用户在 session A 生成中切换到 session B，session A 的 END 事件到来时， session B 的 isGenerating 被置 false，发送按钮恢复，用户发出第二条消息， 与主进程仍在运行的 session A loop 产生竞态。

修复：END handler 加一行 if (d.sessionId !== activeSessionId()) return 在 isGenerating 重置之前。
BUG D · 无并发保护

主进程 chat() 可被重复调用

AgentChatPresenter.chat() 进入时直接 set state = generating， 但没有检查当前是否已在 generating。 若渲染进程侧的 isGenerating 因 Bug C 被误清，用户可以触发第二次 chat()， 主进程会为同一 sessionId 启动两个并行的 agentic loop， 共享同一 messages[] 上下文（contextBuilder 每次从 DB 重建）， 但 assistantMessageId 不同，写 DB 时产生两条 assistant 消息。

修复：chat() 开头检查 if (this.sessionStates.get(sessionId) === "generating") return。
